# 社区运营与互动指南

## 1. 社区目标

GitPlaybook 的社区不是“越热闹越好”，而是围绕一个明确目标：**让第一次接触开源协作的人，完成一次有质量的 Issue 或 PR。**

因此，社区运营优先做三件事：

1. 降低第一次提问和第一次贡献的门槛。
2. 让每个 Issue 都得到可操作的回应。
3. 把课堂使用中的真实问题沉淀为课程改进。

## 2. 角色

| 角色 | 职责 |
| --- | --- |
| Maintainer | 合并 PR、发布版本、维护路线图、处理行为准则事件 |
| Reviewer | 在 48 小时内给出第一轮 review，至少检查测试与可访问性 |
| Contributor | 提交 Issue / PR，按模板提供复现步骤与验证方式 |
| Teacher | 在课堂中使用项目，反馈课程节奏与概念难点 |

## 3. Issue 规范

使用仓库自带的 Issue 模板：

- **Bug report**：期望行为、实际行为、复现步骤、浏览器/系统、截图。
- **Feature request**：使用场景、建议方案、备选方案、是否愿意提交 PR。
- **Question**：先搜索文档和已有 Issue，再描述你卡在哪一步。

标签建议：

| 标签 | 含义 |
| --- | --- |
| `good first issue` | 有明确边界，适合第一次贡献 |
| `help wanted` | 维护者欢迎外部实现 |
| `teaching` | 涉及课程脚本或教学法 |
| `a11y` | 可访问性 |
| `bug` | 可复现的缺陷 |
| `docs` | 文档改进 |

## 4. 响应节奏

- 新 Issue：48 小时内给出首次回应（确认、追问或标记）。
- 新 PR：72 小时内给出第一轮 review。
- `good first issue`：维护者提供文件位置、验收标准和可能的实现提示。
- 行为准则事件：24 小时内私下处理。

这些是目标，不是 SLA。维护者会在无法及时响应时在 Issue 中说明。

## 5. 邀请同学参与的具体做法

课程要求“邀请同学进行 Issue 讨论、star、watch”。可以按以下步骤完成，既真实又对项目有帮助：

### 第一步：请同学试用

给同学一个具体任务，而不是“帮我点个 star”：

> 请打开 <https://github.com/<your-name>/GitPlaybook>，完成实验 03。如果你在“保留双方”之外想到了更好的解决方式，请在 Issue 里描述你的合并结果。

### 第二步：请同学提 Issue

提供一个模板：

```text
标题：[实验 03] 我对冲突解决有不同做法
环境：Chrome 131 / Windows 11
我做了什么：……
我期望：……
实际发生：……
我的建议：……
```

### 第三步：维护者回复

在 Issue 中公开回复，哪怕只是确认：

- 感谢具体反馈。
- 复现或说明无法复现。
- 给出下一步：`accepted`、`needs info`、`good first issue`。
- 如果采纳，关联 PR 并说明会在哪个版本发布。

### 第四步：请同学 star / watch

Star 表示“这个项目对我有用”，Watch 表示“我想跟进后续讨论”。可以在课堂上说明两者的区别，而不是把它当作打卡任务。

### 第五步：把互动沉淀到报告

截图建议：

- 仓库首页的 star / watch 按钮与计数。
- 一条有来有回的 Issue 对话。
- 一个已合并的 PR（包含 review 评论）。
- 分支列表或 Network graph。

## 6. 度量

| 指标 | 说明 | v0.1 目标 |
| --- | --- | --- |
| Stars | 项目被收藏的数量 | 30 |
| Forks | 被复制/二次开发的数量 | 8 |
| Issues | 真实问题与建议 | 10 |
| 外部 PR | 非维护者提交的 PR | 3 |
| 首次响应时间 | Issue 首次回复 | < 48h |
| 课程试用 | 使用过的班级/社团 | 2 |

数字不是目的。一个包含完整复现步骤的 Issue，比十个“支持”更有价值。

## 7. 不做什么

- 不购买 star 或互刷 star。
- 不把“star 数”作为唯一成功指标。
- 不承诺无法维护的功能。
- 不对课堂作业提交做虚假的“已合并”记录。

开源社区的信用来自可验证的协作痕迹，而不是截图数量。
